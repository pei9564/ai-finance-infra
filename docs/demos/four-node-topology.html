ADR-001 · 叢集硬體基線

四節點異質 home-lab
約束如何反推出每個節點的角色

3 台 Linux laptop + 1 台 dev workstation，單張可用 GPU、單顆旋轉硬碟。點任一節點看它的規格與分派理據，切換「現況 / K3s 目標」看 workload 如何重新落位。

Status: docker-compose 現況運行中 · K3s 遷移規劃中

01主導設計的硬約束

所有角色分派都不是「想怎麼擺」，而是被下面這幾條物理事實逼出來的：

⛔ 五條無法繞過的事實

① 唯一可用的現代 GPU 在 node-a（Ampere cc 8.6）；node-c 的 Maxwell cc 5.0 被 PyTorch 停止支援，等於沒有。
② 唯一的旋轉硬碟 在 node-c — 淘汰它扛任何延遲敏感角色（etcd、Postgres）。
③ 30 GB 記憶體集中在沒 GPU 的 node-b — 它天生是有狀態服務 + control-plane 的人選。
④ 全是會 sleep 的 laptop、僅 WiFi — 3-node etcd HA 不可行，HA 被明確取捨掉。
⑤ node-a 正在 swap-thrash（16 GB 上同時扛 Whisper + Postgres + Redis）— 這才是遷移 K3s 的主因。

03為什麼遷移：資源隔離，不是 HA

在這組 laptop 規格的叢集上，HA 是被取捨掉的。遷移的真正目的是把有狀態服務從 GPU node 拔走：

  1. 問題的根源是共置。Production workload 跟 Whisper STT 擠在同一台 node-a 的 16 GB 上 → 持續 swap 壓力。
  2. 把 Postgres / Redis / queue broker 搬到 node-b（30 GB、無 GPU 爭用），讓 node-a 把全部 16 GB RAM + 4 GB VRAM 都留給 inference。
  3. 冷資料落到 node-c 的 ~900 GB 閒置 HDD（cold backup + object storage）— 把劣勢硬碟轉成優勢角色。
  4. 接受 node-b 的 SPOF 風險。laptop 會 sleep，但在單人 home-lab，cluster 簡潔性 > HA — 這是清醒的取捨，不是疏忽。
