ADR-005 · 架構決策紀錄

本地推論的 Serving Runtime 選型
vLLM vs. Ollama vs. llama.cpp

一個被「單張 4 GB GPU、且與 Whisper STT 共卡」這條物理約束反推出來的決策。拖動下面的滑桿，看約束如何翻轉答案。

Status: Proposed — runtime 已定，最終模型 pick 待實跑驗證

01面臨的挑戰

上游決策（ADR-004）已拍板：LLM 推論要從外部 API 搬回自架本地模型，以達成零雲洩漏。本篇只回答一個問題——用哪個 serving stack 把模型跑起來？

⛔ 最硬的物理約束

node-a 只有 ~4 GB VRAM，而且 Whisper STT 已經佔住同一張卡。本地 LLM 沒有專屬 GPU 可用——它必須跟 STT 搶 VRAM。負載是單人、批次、逐則摘要、非即時，所以吞吐量不是首要；「在約束內跑得起來、又接得上既有 gateway」才是。

02VRAM 預算模擬器

三個 runtime 的差異，在這張卡的容量下會被放大。調整 VRAM 總量與 STT 是否共卡，看每個框架是否裝得下、以及情境推薦如何變化。

vLLMPagedAttention · 無 CPU offload

模型基準：Qwen2.5-3B-Instruct，Q4_K_M 量化下約 2 GB（選 Qwen 是因為下游是繁中金融摘要，中文能力 > 英文 benchmark）。vLLM 另計 ~2 GB baseline overhead 且不做 CPU offload；Ollama / llama.cpp 裝不下的層自動 offload 到 CPU。

03三個候選，逐一拆解

vLLM 本場景出局

  • 高吞吐（PagedAttention），production-grade
  • 原生 OpenAI-compatible API
  • VRAM baseline overhead 高（預設 gpu_memory_utilization=0.9）
  • 幾乎不做 CPU offload — 4 GB 放不下就是放不下
  • 為「有專屬 GPU 的高並發服務」而生，與 STT 共卡極脆弱

Ollama 選定

  • 一行起服務；內建模型管理
  • GGUF + GPU/CPU 混合 offload，4 GB 也跑得動
  • OpenAI-compatible endpoint → 接既有 gateway 是「換 endpoint」等級
  • 吞吐不如 vLLM；並發/批次控制較陽春

llama.cpp 可行但虧

  • 最省資源；offload 層數可最細調
  • 要自己包 HTTP server / API / 模型管理
  • 維運成本高 — 等於重做 Ollama 已經給的東西

04決策與理據

選定 Runtime = Ollama，模型暫定 Qwen2.5-3B-Instruct Q4_K_M。推理鏈：

  1. 物理約束先淘汰 vLLM。4 GB 且與 STT 共卡，而 vLLM 無 CPU offload — 直接出局，與品質無關。
  2. 剩下 Ollama vs 裸 llama.cpp，兩者推論能力同源（Ollama 就是 llama.cpp 的封裝），差別在維運。
  3. Ollama 把 llama.cpp 包成 OpenAI-compatible API + 模型管理，接上 05-15 已建好的 gateway 介面只是換 endpoint；裸 llama.cpp 要自己重做這層。
  4. 吞吐劣勢在此負載下不是瓶頸（單人、批次、非即時摘要），所以放棄吞吐換維運成本是划算的。
